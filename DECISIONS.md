## 2026-09-21 — Stage 1: auth, roles, brands and access (Vishnu + Claude)

- 2026-09-21 — **404 for invisible, 403 for not-permitted.** A brand you hold no grant on, a brand id that does not exist, and an archived brand seen by a member all return the same 404 with a **byte-identical body**; an action above your grant on a brand you *can* see returns 403. The PRD did not say, and UI_PLAN §5 covered only the 403 case. Two 404s that differ in wording or shape still let an outsider walk the id space — hence the equality assertion in `tests/rbac/` rather than a status-code check — Vishnu
- 2026-09-21 — An **admin-only mutation answers 403 uniformly for every brand id**, because the role gate runs before any lookup. That is not a leak — the reply does not depend on the brand — so the test asserts uniformity rather than forcing a 404 through a role gate. Written down because the first version of the test asserted 404 and was wrong — Claude
- 2026-09-21 — **FR-4 amended: invites do not need SMTP.** FR-10 (the SMTP profile) is P1 and lands in Stage 4, so invites literally could not be emailed in Stage 1. An invite returns its link once, in the creation response, and the UI shows it with a copy button. When SMTP arrives, emailing becomes an addition, not a rewrite — Vishnu
- 2026-09-21 — **Invite and reset tokens are show-once, hash-only.** Only the SHA-256 is stored, so a database leak cannot be replayed into an account. A lost link is recovered by "New link", which rotates the token and kills the previous one — chosen over storing the token encrypted for re-display — Vishnu
- 2026-09-21 — **One `invites` table serves invites and password resets**, separated by `purpose`, because the rules are identical (hash only, single use, expiry, revocable) and duplicating that logic is how one copy drifts. Expiry differs: 7 days for an invite, 24 hours for a reset. The purpose is part of the token lookup, so the two flows cannot be crossed — Claude
- 2026-09-21 — **Sessions are opaque ids in Redis**, not a stateless token: deactivating a user, resetting their password or changing their own must revoke access on the next request, which a self-contained token cannot do. Redis already runs with `appendonly yes` and a volume, so a restart does not sign everyone out — Vishnu
- 2026-09-21 — **Login rate limits: 10 per 15 min per IP, 5 per 15 min per email**, sliding window in Redis, both consumed before any credential check so a flood cannot probe passwords. The email is hashed into the key — the counter does not need to know who it is counting. An unknown email and a wrong password return byte-identical 401s, and one argon2 verify always runs, so neither body nor timing reveals whether an account exists — Vishnu
- 2026-09-21 — **CSRF is double-submit** and the token **rotates on sign-in** (session fixation). The frontend therefore reads the cookie per request rather than caching it — a cached token 403s every mutation after login, which is how the rotation was found — Claude
- 2026-09-21 — **The seeded super admin starts with `must_change_password`.** Every route except the change-password screen refuses until it is done, so the password in `infra/.env` stops being a working credential the first time it is used. The seeder refuses to create an account when the password is blank rather than making one with no way in — Vishnu
- 2026-09-21 — **Lockout guards:** nobody can demote, deactivate, un-grant or password-reset themselves, and the last *active* super admin cannot be demoted or deactivated (an inactive one does not count as cover). These are the clicks with no undo from inside the UI — Vishnu
- 2026-09-21 — **Auth events are audited**: login success and failure, rate-limit trips, logout, password change, reset issued and used, and sessions revoked on deactivate. Email and IP are recorded; the audit service strips any key that looks like a credential before writing, and a test asserts no password reaches the log — Vishnu
- 2026-09-21 — **Archived brands are invisible to members**, grant or no grant, and `archived=all` is forced back to "active" for them rather than trusting the query parameter. Admins see them behind an "Archived" filter — Vishnu
- 2026-09-21 — `exactOptionalPropertyTypes` is **off** in `tsconfig.json`; everything else stays strict. It is not part of `strict`, and TanStack Table's `ColumnDef` is invariant in its value type under it, so every column definition in the app would need a cast — and CLAUDE.md mandates TanStack Table for all tables — Claude
- 2026-09-21 — shadcn primitives are **hand-written against the THEME.md tokens** rather than pulled with `npx shadcn add`. The CLI appends its own colour variables to the stylesheet it is pointed at, which would put a second palette next to THEME.md's. ## 2026-09-22 — the runs that sat at "queued"

- 2026-09-22 — **Connection pools are cached per event loop, not per process.** "Test login" left every second run stuck at `queued` for ever. The worker calls `asyncio.run()` once per Dramatiq message across two threads, and both the SQLAlchemy engine and the redis-py pool were module globals — so the second task on a thread checked out a connection belonging to a loop that had already closed: `RuntimeError: got Future attached to a different loop`. It struck inside `session.get(Run, run_id)`, *before* the run's own error handling, so nothing marked the run failed and the UI waited on it indefinitely. The run table shows the signature plainly: succeeded, queued, succeeded, queued. `get_engine()`, `get_session_factory()` and `get_pool()` now key their cache on the running loop, and `dispose_engine()`/`close_redis()` close only the running loop's own — a task cleaning up must not pull the pool out from under another thread. The API and scheduler each run one long-lived loop, so their pooling is unchanged — Claude
- 2026-09-22 — **A task that dies outside the run's own error handling still ends the run.** `_execute` wraps the whole body, not just `run_tasks_for`, and `_mark_crashed` disposes the possibly-poisoned engine before opening a clean session to record the failure. A run left in the status it was created with is worse than a failed one: the UI has nothing to show and no reason to stop waiting — Claude
- 2026-09-22 — **`task.failed` logs `error_code`, not `code`.** `code` is in `SENSITIVE_KEYS` — correctly, since an OTP is a code — so every failure logged its classification as `***`, redacting the one field that explained it — Claude
- 2026-09-22 — **The api container mounts `tools/` read-only.** `tests/tools/test_redact_eml.py` loads `tools/redact_eml.py` by path, and it was not mounted, so `make test` failed at collection and ran nothing at all. Same root cause as the infra files above: the suite runs in a container that mounts only `backend/` — Claude

### Still open

- Nothing reaps a run whose worker dies between `queued` and the first event. The crash handler above covers an exception, but not a `SIGKILL`ed worker. The executor already writes `run_heartbeat:{run_id}` with a 300s TTL, so a reaper in the scheduler is the natural home — Stage 4.
- 2026-09-22 — **"Test login" was a no-op that reported success.** `run_tasks_for` began `if not tasks: set_status("succeeded")`, and a test login has no tasks by definition — so it never opened a browser, never touched the adapter, and told the operator the login worked. `test_only` was passed to `_execute` and then dropped. It now runs the same sequence as a real run up to and including the sign-in, skipping only the brand step, because a test that proves something other than what a real run does proves nothing. A test login on Zepto now correctly ends `browser_started → signing_in → NOT_IMPLEMENTED` — Claude
- 2026-09-22 — **`UndecryptableSecret` is `CREDENTIAL_UNREADABLE`, not `UNKNOWN`.** A mailbox saved under an earlier `UNIQCAI_MASTER_KEY` failed with "Something unexpected went wrong", marked *retryable* — and no retry can conjure a dropped key back. It now names the cause and says the credential has to be entered again. This is the failure mode `make rotate-key` exists to prevent, so it should read as a key problem, not a portal problem — Claude

## 2026-09-22 — the Zepto Ads adapter, corrected

- 2026-09-22 — **`openpyxl` was never a declared dependency, and the Zepto adapter cannot work without it.** `sniff_header` imports it to read a downloaded workbook's header row, inside a `try/except Exception` that logs `zepto.header_unreadable` and returns `[]`. It was missing from both images, so *every* Zepto download had an unreadable header, `sniff_report_type` always returned `None` — and the collector's guard was `if actual is not None and actual != report_name`, which falls **through** on `None`. Every downloaded file would therefore have been filed as whatever report the collector happened to be waiting for, silently and 100% of the time. The guard is now `if actual != report_name`, which is what the prototype did (`UNMATCHED_`), and `openpyxl` is a declared dependency — Claude
- 2026-09-22 — **An unreadable file is rejected, not claimed.** Stated separately because it is the rule, not the bug: the report centre never says which report a row produced, so the file's own header is the only honest answer. "I could not read it" is not evidence that it is the one we asked for. Same failure class as `WRONG_ACCOUNT` — a complete, believable file for the wrong thing — arriving by a different door — Claude
- 2026-09-22 — **The report-centre baseline is taken once per run, not once per report.** `Requested At` has minute resolution, so rows are excluded with `<=`; re-taking the baseline per report made a second report requested inside the first one's minute unable to ever see its own row — full deadline, retry, same again. The prototype took one baseline per batch of six for this reason. Held in a `ContextVar` beside the run's brand, with a sentinel separating "not taken yet" from a genuinely empty report centre — Claude
- 2026-09-22 — **The fallback cutoff compares like with like.** `row_time` parses the portal's own clock and returns naive IST; `requested_at` was `datetime.now()`, the container's UTC, 5.5 hours behind. On the empty-report-centre path that made our own row look older than the cutoff. It is now naive IST, and the prototype's **two-minute clock grace** is restored — the portal's clock is not ours — Claude
- 2026-09-22 — **A transient `inner_text()` failure no longer means "no data".** `_card_stable_with_data` returned `False` on any exception, which becomes `EmptyReport` upstream — non-retryable — so one flaky read reported a report that has data as having none. The prototype set the snapshot to `None` and kept looping; it does that again — Claude
- 2026-09-22 — **`EmptyReport` no longer turns a run red.** `base.py` said "the run should not go red and the task should not be retried" and the `ErrorCode` was `unhealthy=False`, but nothing in the executor honoured it, so a quiet report failed the run and burned a failure screenshot. It is now a recorded non-failure: task `succeeded` with `error_code=EMPTY_REPORT` and a warning event. `succeeded` rather than a new `empty` status because the task did run to completion — and a new status would need a migration for this one case — Claude
- 2026-09-22 — **`TargetClosedError` is `NAVIGATION_FAILED`, not `DOWNLOAD_FAILED`.** A browser that never launched has not failed to download anything, and "The report did not download" sent a reader to the portal when the problem was a stale profile lock on this side — Claude

## 2026-09-22 — schedules

- 2026-09-22 — **A missed schedule fires once, then jumps forward.** `next_run_at` advances from *now*, not from the slot that was missed, so a scheduler down for three days fires once on return rather than queueing three runs that all contend for one account lock. Rolling ranges recover the data anyway. Neither PRD nor SYSTEM_DESIGN stated a catch-up policy; this is the decision — Vishnu
- 2026-09-22 — **The first cut is daily / weekly / monthly, no raw cron.** FR-27's Advanced mode and FR-26's category-level auto-inclusion wait until the simple case has run unattended. The frequency is nonetheless *stored* as cron, so adding modes later needs no migration and one well-tested library evaluates it rather than a home-grown recurrence rule — Vishnu
- 2026-09-22 — **The date range is resolved at fire time, never stored.** "The last three days" has to mean something different tomorrow. Fixed ranges are the opposite and exist for backfills — Claude
- 2026-09-22 — **Every rolling preset ends yesterday, not today.** Today's figures are incomplete on every platform, and Instamart renders today and later as disabled in its date picker (`docs/platforms/instamart.md`). So "last 7 days" means seven *complete* days, which is what anyone pulling ads data wants — Claude
- 2026-09-22 — **`schedules` has no `last_run_id`.** It would point at `runs` while `runs.schedule_id` points back, and SQLAlchemy cannot even order the `CREATE TABLE`s for a cycle — it warns on every test run. The list screen's "last result" is the newest run carrying the schedule's id: one indexed query, and it cannot go stale — Claude
- 2026-09-22 — **The preview calls the server.** `POST /schedules/preview` runs the scheduler's own `resolve_period`, so what the form shows is what will happen. Computing it in the browser would be a second implementation free to drift from the one that matters — Claude
- 2026-09-22 — **The scheduler sweeps stale runs.** Nothing did. A killed worker left a run `running` for ever holding its account lock, so every later run for that login queued behind one that would never finish. A run whose `run_heartbeat:{id}` has been silent for ten minutes becomes `failed (WORKER_LOST)` and its lock is released — the same class of problem as the stale Chromium profile lock, and the second half of what `tick()` was always specified to do — Claude
- 2026-09-22 — **Monthly schedules stop at day 28.** Day 29–31 would skip February, or fire on a date that does not exist. Offering only what fires every month is better than explaining afterwards why March was missed — Claude
- 2026-09-22 — **`max_range_days` is enforced, not merely stored.** Four platforms have a real per-report cap (Zepto OOS visibility 7, Blinkit PO 30, Instamart granular 31, FK Minutes 31) and the portal only says so after a sign-in and a queued export. Refusing at run creation costs nothing and saves a run that could only fail — Claude
- 2026-09-22 — **The account pick is ordered.** `.first()` with no `ORDER BY` meant a brand with two logins on one portal ran whichever the planner returned, and which one could change between runs. Oldest connection wins — Claude
- 2026-09-22 — **Zepto downloaded its first report end to end.** Run 64: existing session reused, brand verified against the connection, one Sponsored Products Campaign workbook stored byte-for-byte with its checksum, period and `is_latest`. Three things had to be fixed to get there, all recorded above and below — Claude
- 2026-09-22 — **`_DownloadCatcher` must wrap its handler in a closure.** The port replaced the prototype's `def _on_download(d): self.downloads.append(d)` with a bare `self.downloads.append`, and Playwright introspects an event handler: for a bound method it reads `_pw_impl_instance_` off `__self__`, which a plain list does not have. Registering it raised before a single download could arrive, and the "simplification" is exactly what CLAUDE.md rule 4 warns against — Claude
- 2026-09-22 — **A test login now reports the in-portal brand instead of skipping the step.** `select_brand` is the only place the portal's own id for the business is readable, and the adapter puts it in the `AccountChoiceRequired` message precisely so it can be copied onto the connection. A test login has nothing to verify against, so it treats that exception as information and succeeds — failing there would hide the very thing the operator signed in to find out — Claude
- 2026-09-22 — **A run-level failure now marks its tasks.** Sign-in and brand verification happen outside the task loop, so a failure there left every task on the `queued` it was created with and the run page's Reports panel showed nothing at all. The commonest case is a connection that does not name its in-portal brand, where the reason is the only thing that helps — Claude
- 2026-09-22 — **The connection's in-portal brand is editable from the brand page.** It could only be set in the wizard, *before* the first sign-in — but the value is a portal id only readable *after* one. So the sequence test login → copy from the timeline → paste → run was impossible without SQL. The row warns when it is unset, because until then every download fails — Claude

## 2026-09-22 — offline copies of the client pages

- 2026-09-22 — **`docs/client/offline/` holds a self-contained copy of each page, built by `docs/client/_tools/build_offline.py`.** One file each, no network, no asset folder: open it from a USB stick or send it as an attachment.
