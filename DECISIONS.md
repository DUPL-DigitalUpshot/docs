## 2026-09-21 — Stage 1: auth, roles, brands and access (Vishnu + Claude)

- 2026-09-21 — **404 for invisible, 403 for not-permitted.** A brand you hold no grant on, a brand id that does not exist, and an archived brand seen by a member all return the same 404 with a **byte-identical body**; an action above your grant on a brand you *can* see returns 403. The PRD did not say, and UI_PLAN §5 covered only the 403 case. Two 404s that differ in wording or shape still let an outsider walk the id space — hence the equality assertion in `tests/rbac/` rather than a status-code check — Vishnu
- 2026-09-21 — An **admin-only mutation answers 403 uniformly for every brand id**, because the role gate runs before any lookup. That is not a leak — the reply does not depend on the brand — so the test asserts uniformity rather than forcing a 404 through a role gate. Written down because the first version of the test asserted 404 and was wrong — Claude
- 2026-09-21 — **FR-4 amended: invites do not need SMTP.** FR-10 (the SMTP profile) is P1 and lands in Stage 4, so invites literally could not be emailed in Stage 1. An invite returns its link once, in the creation response, and the UI shows it with a copy button. When SMTP arrives, emailing becomes an addition, not a rewrite — Vishnu
- 2026-09-21 — **Invite and reset tokens are show-once, hash-only.** Only the SHA-256 is stored, so a database leak cannot be replayed into an account. A lost link is recovered by "New link", which rotates the token and kills the previous one — chosen over storing the token encrypted for re-display — Vishnu
- 2026-09-21 — **One `invites` table serves invites and password resets**, separated by `purpose`, because the rules are identical (hash only, single use, expiry, revocable) and duplicating that logic is how one copy drifts. Expiry differs: 7 days for an invite, 24 hours for a reset. The purpose is part of the token lookup, so the two flows cannot be crossed — Claude
- 2026-09-21 — **Sessions are opaque ids in Redis**, not a stateless token: deactivating a user, resetting their password or changing their own must revoke access on the next request, which a self-contained token cannot do. Redis already runs with `appendonly yes` and a volume, so a restart does not sign everyone out — Vishnu
- 2026-09-21 — **Login rate limits: 10 per 15 min per IP, 5 per 15 min per email**, sliding window in Redis, both consumed before any credential check so a flood cannot probe passwords. The email is hashed into the key — the counter does not need to know who it is counting. An unknown email and a wrong password return byte-identical 401s, and one argon2 verify always runs, so neither body nor timing reveals whether an account exists — Vishnu
- 2026-09-21 — **CSRF is double-submit** and the token **rotates on sign-in** (session fixation). The frontend therefore reads the cookie per request rather than caching it — a cached token 403s every mutation after login, which is how the rotation was found — Claude
- 2026-09-21 — **The seeded super admin starts with `must_change_password`.** Every route except the change-password screen refuses until it is done, so the password in `infra/.env` stops being a working credential the first time it is used. The seeder refuses to create an account when the password is blank rather than making one with no way in — Vishnu
- 2026-09-21 — **Lockout guards:** nobody can demote, deactivate, un-grant or password-reset themselves, and the last *active* super admin cannot be demoted or deactivated (an inactive one does not count as cover). These are the clicks with no undo from inside the UI — Vishnu
- 2026-09-21 — **Auth events are audited**: login success and failure, rate-limit trips, logout, password change, reset issued and used, and sessions revoked on deactivate. Email and IP are recorded; the audit service strips any key that looks like a credential before writing, and a test asserts no password reaches the log — Vishnu
- 2026-09-21 — **Archived brands are invisible to members**, grant or no grant, and `archived=all` is forced back to "active" for them rather than trusting the query parameter. Admins see them behind an "Archived" filter — Vishnu
- 2026-09-21 — `exactOptionalPropertyTypes` is **off** in `tsconfig.json`; everything else stays strict. It is not part of `strict`, and TanStack Table's `ColumnDef` is invariant in its value type under it, so every column definition in the app would need a cast — and CLAUDE.md mandates TanStack Table for all tables — Claude
- 2026-09-21 — shadcn primitives are **hand-written against the THEME.md tokens** rather than pulled with `npx shadcn add`. The CLI appends its own colour variables to the stylesheet it is pointed at, which would put a second palette next to THEME.md's. ## 2026-09-22 — the runs that sat at "queued"

- 2026-09-22 — **Connection pools are cached per event loop, not per process.** "Test login" left every second run stuck at `queued` for ever. The worker calls `asyncio.run()` once per Dramatiq message across two threads, and both the SQLAlchemy engine and the redis-py pool were module globals — so the second task on a thread checked out a connection belonging to a loop that had already closed: `RuntimeError: got Future attached to a different loop`. It struck inside `session.get(Run, run_id)`, *before* the run's own error handling, so nothing marked the run failed and the UI waited on it indefinitely. The run table shows the signature plainly: succeeded, queued, succeeded, queued. `get_engine()`, `get_session_factory()` and `get_pool()` now key their cache on the running loop, and `dispose_engine()`/`close_redis()` close only the running loop's own — a task cleaning up must not pull the pool out from under another thread. The API and scheduler each run one long-lived loop, so their pooling is unchanged — Claude

- 2026-09-23 — **Instamart has no portal password.** The live page is `#email-input` plus a "Send OTP" button and nothing else, confirming the prototype's note. A password supplied for this portal belongs to the mailbox, not the login; `login()` fills one only if a field is actually present, so it is harmless either way — Claude
- 2026-09-23 — **`page_message` is a coroutine and was not awaited** in both new adapters, so every login failure reported `<coroutine object page_message>` instead of the portal's own words. It cost a diagnosis before it was spotted — Claude
- 2026-09-23 — **A run-level failure now carries the adapter's own message.** The handler used the generic `ErrorCode` text, so an adapter saying which step failed and why was flattened to "The portal rejected the credentials". The code is still appended, so runs stay filterable — Claude
- 2026-09-23 — **Login diagnostics log the page's shape, never its content.** Element tag, type, name, id, placeholder, maxlength and label — no values, because at that point the page holds a typed credential (rule 1). It turned "it did not work" into "here is what the page offers", and found the real login form in one run where the saved captures were empty React shells — Claude

## 2026-09-23 — Brand discovery and mapping

- 2026-09-23 — **The portal's own brand list replaces typing `portal_brand_selector` from memory.** The value is only knowable after signing in once, so the flow was: run Test login, read the brand out of a sentence in the run timeline, paste it into a text box. A typo fails a run; a wrong paste on an agency login produces complete, believable files about the wrong business. `legacy/blinkit/partnersbiz_session.py:276` had already reached this conclusion — its `list_entities()` exists "so a person can be shown the real list and pick, instead of typing a name from memory and hoping the automation lands on it" — Claude
- 2026-09-23 — **`list_brands` is a separate contract method from `select_brand`, and concrete rather than abstract.** They answer different questions: `select_brand` reads back the business the session is *on* (rule 9), while `list_brands` asks what the login *carries*. Making it abstract would have broken every adapter and the stub for a capability most portals do not have, so portals opt in through `capabilities` — Claude
- 2026-09-23 — **`BrandList.unavailable` is not an empty list.** Blinkit's business picker only exists before a business is chosen and cannot be shown again without signing out. Reporting that as "no brands" would tell an operator an agency login serves one business, which is the wrong thing to believe about exactly the logins this feature exists for — Claude
- 2026-09-23 — **Discovery runs on test logins only.** A production run has already been told which brand it is for, and opening a brand switcher mid-run would add DOM work and a failure mode to a download that was going to succeed. It also never fails a sign-in: the operator signed in to test a login, and an unreadable brand list is a worse timeline entry, not a worse outcome — Claude
- 2026-09-23 — **A suggested match is never pre-ticked; an identical name is.** The chosen design was suggest-and-confirm, and a pre-selection accepted without being read is the silent wrong-brand failure in a new costume. So `exact` compares the *raw* words (case and punctuation aside) and arrives ticked, while suffix-stripping — which makes `DEL MONTE FOODS` match `Del Monte` — only ever produces `suggested`, unticked, with a visible badge. Stripping suffixes to decide identity would make `Del Monte` and `Del Monte Foods` indistinguishable and pre-tick one of them arbitrarily — Claude
- 2026-09-23 — **A tie is no suggestion at all.** Two brands fitting equally well ("Nestle Foods" and "Nestle Waters" for a portal saying "Nestle") returns null rather than picking one: a coin toss presented as a recommendation is worse than silence, because nothing invites the operator to look twice at it — Claude
- 2026-09-23 — **`connections` gained the unique constraint it never had.** Uniqueness on `(brand_id, account_id)` was a read-then-409 in the router and a read-then-upsert in the wizard, both racy. Mapping several brands in one transaction is the shape that turns that race into duplicate rows — which would run the same download twice and store two files with different checksums. `0007` deduplicates before constraining, keeping the lowest id, which is the row the app's own check would have kept — Claude
- 2026-09-23 — **Instamart's brand control is `side-panel-v2-account-switcher-trigger`, and its options are plain `div`s.** Both were read off the live DOM after selectors inferred from a screenshot matched nothing. The options carry no role and no test id, so they are reachable only through the switcher's container — and the switcher renders the avatar's single initial alongside them, hence the same `3 < len(name) < 60` bound `_brands_on_page` uses — Claude
- 2026-09-23 — **Discovery never chooses.** `list_brands` opens the switcher and closes it with Escape, leaving the session on the business it arrived on. A discovery step that silently reassigns which business the rest of the run is about is a rule-9 failure wearing a helpful face — Claude

## 2026-09-23 — Mailboxes are configured by provider, not by hostname

- 2026-09-23 — **The mailbox form asks which provider, not which IMAP host.** Typing `imap.gmail.com` by hand is a spelling test whose failure arrives three minutes later, when the mailbox is tested — and a wrong host is indistinguishable from a wrong password at that point. The host and port are still stored and sent exactly as before, so nothing changed behind the form — Claude
- 2026-09-23 — **Zoho is listed three times, deliberately.** `imap.zoho.in`, `imap.zoho.com` and `imap.zoho.eu` are separate services and an account exists in exactly one region; the other two reject it in a way that reads as a bad password. One combined "Zoho" entry would not remove that guess, only move it somewhere less visible. The legacy config supported all three, which is where the list comes from — Claude
- 2026-09-23 — **A custom domain gets no guess.** `providerForEmail` returns null for anything it does not recognise, because `ops@digitalupshot.com` could be Google Workspace, Microsoft 365 or neither. A host filled in on a coin toss produces a mailbox that looks configured and fails on first use, which is worse than an unfilled field — nothing prompts anyone to check it — Claude
- 2026-09-23 — **The address stops steering the picker once the picker is used.** Otherwise someone choosing Google Workspace for a custom domain would have it undone by typing the rest of their email — Claude
- 2026-09-23 — **Host and port are hidden unless "Other" is chosen.** A provider fixes both, and leaving them on screen invites an edit that turns a working mailbox into one that fails on next use. An existing mailbox opens on its own provider rather than reading "Other" — Claude

## 2026-09-23 — the setup-and-access diagram

- 2026-09-23 — **`setup.html` answers the half `architecture.html` does not: what you create, in what order, and who can then see it.** Twelve blocks for the objects rather than the services, two lenses (Admin and Brand team), three walkthroughs — connect a brand, give someone access, something broke. Offline bundle and `SETUP.md` only; it is a working reference, not something to send, so it has no published link — Claude
- 2026-09-23 — **The cardinalities the page asserts, so a later model change has something to contradict.** One mailbox serves many logins (`platform_accounts.mailbox_id`, nullable, `ON DELETE RESTRICT`). One login serves many portals (`account_portals`, composite PK, health per row). A connection is brand × **account**, not brand × portal, unique on the pair. A schedule names a brand and report keys and never an account — the login is resolved at run creation. One grant per person per brand (`brand_grants` composite PK), `categories` NULL meaning every category. Each was read from the model before it was drawn, not assumed — Claude
- 2026-09-23 — **A mailbox is not a gate, and the page says so.** `mailbox_id` is nullable and an account with none signs in fine right up to the step that needs a code; `test_mailbox_not_a_gate.py` locks that down. Drawing it as a prerequisite would have taught the opposite of what the system does — Claude
- 2026-09-23 — **`default_report_keys` is a UI default and nothing more.** Nothing in `create_runs` reads it; a run takes its report keys from the request or from `schedules.report_keys`. The page says "a starting point, not a rule" rather than implying a connection constrains what can be collected — Claude
- 2026-09-23 — **An unset `portal_brand_selector` is only fatal where the login opens more than one business.** On a single-business login, blank is correct and the wizard says so. The earlier draft of this page claimed every collection fails without it, which would have sent people hunting for a value that does not exist — Claude

### Two things found while reading, worth fixing separately

- 2026-09-23 — **`otp_rules` has no unique index on `(portal_key, account_id)`**, but `_resolve` in `otp_rules/router.py` and `resolve_otp_rule` in `rpa/executor.py` both call `.scalar_one_or_none()`. A duplicate row raises `MultipleResultsFound` at sign-in time rather than being refused at save time. A migration adding the constraint is the fix — Claude
- 2026-09-23 — **The API and the executor resolve an OTP rule differently.** `resolve_otp_rule` merges field by field, so an override row with a NULL sender falls back to the adapter's sender for that field alone; the API's `_resolve` returns the row whole. The rule an admin reads on screen is therefore not always the rule that runs — Claude
