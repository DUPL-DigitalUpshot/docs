Each column of each sheet, and what would happen to it at each stage: Raw, Staging and Our database.

Three stages: Raw → Staging → Our database

The same three stages as Zepto. Raw and Staging keep every column exactly as Blinkit sent it. Columns are treated differently only in Our database.

Stage 3 · proposed

Our database

wh.fact_ad + wh.dim_*
What
One clean row per day, campaign and keyword (or category, or sub-campaign). Bid-level rows are summed.
Kept
Forever. Blinkit changes sales for 7 days after the day, so we re-pull the last 10 days and newer files replace those days; old rows are marked, not deleted.
The checks before data reaches our database
  • Every expected column is present.
  • Every row of the sheet is loaded exactly once.
  • Totals of Spend, Impressions and Sales match the sheet.
  • Blinkit's RoAS and CTR match our own calculation (at most 1% of rows may differ).
  • The Manufacturer is the login's (needs a brand rule first, see below).
  • Every row's date falls inside the requested range.
  • Rows that share a key are summed only where Blinkit splits a day by bid.
  • Σ daily spend equals the MTD sheet's served budget, within ₹1.

The treatments in Our database

Stored as number

A number in its own column, added up across rows and days. Direct and indirect parts both feed the total, and the direct part is kept too.

Kept as-is

Stored exactly as Blinkit wrote it, never added up: the CPM bid, the daily budget, rank, reach, unique clicks, the on-hold time, MTD control figures.

Label

Campaign, keyword, category, match and pacing type. They go to lookup tables or become the row's key.

Row date

Blinkit has real daily dates, unlike Zepto, so the row's date comes from the file.

Checked, then recalculated

RoAS and CTR. We check Blinkit's value against our own calculation, then recalculate from the totals in dashboards.

Brand check

The Manufacturer column. Blinkit names the manufacturer, not the brand, so a rule mapping it to our brand is needed first (open question Q21).

Before go-live

Found while preparing this proposal:
  • Manufacturer → brand. Both Blinkit connections have no brand selector, so every file would fail the brand check today. One manufacturer can also map to only one of our brands.
  • Product Recommendation labels. Subcampaign ID, Asset and Title have no place in our database yet; the loader would stop the sheet.
  • Dashboard export. No mapping yet. It repeats three MTD sheets with other column names (Keyword → Targeting Value, New Users → New Users Acquired). To load it at all we would need a DD-MM-YYYY date reader and Match Type NA (its category rows), and the ad type from Targeting Type. One file per day works: verified for 1 Sep – 14 Oct.
  • Load one export, not both. The two exports carry identical numbers for the same day; the month-to-date report is the source.
  • Identical rows are real. Blinkit can split one bid level into two identical rows; they are added up, like bid rows. Only a dashboard export spanning two months repeats rows for real, so it is never requested across a month boundary.
  • Settling window. Sales change for 7 days, never 8 or more (measured on settled data). Our setting is 5 days; we propose 10.
  • Duplicate brand. "Del Monte" and "Delmonte" are one client on one Blinkit login; September and October files sit under different brand records.

Added by us on every row

Blinkit's file doesn't contain these, so we add them:
  • Brand (brand_id): the brand whose login downloaded the file, once the manufacturer rule exists.
  • Ad type (ad_product): from the sheet name (Keyword Targeting, Listing Spotlight…), or from Campaign Type on the MTD sheet.
  • Period (period_start, period_end): the range we asked for. The row's own date comes from the file.
  • Where it came from (report_file_id, load_id, observed_at): a link back to the original file. A newer file replaces restated days (superseded_at) rather than deleting them.
