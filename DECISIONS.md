## 2026-09-21 — Stage 1: auth, roles, brands and access (Vishnu + Claude)

- 2026-09-21 — **404 for invisible, 403 for not-permitted.** A brand you hold no grant on, a brand id that does not exist, and an archived brand seen by a member all return the same 404 with a **byte-identical body**; an action above your grant on a brand you *can* see returns 403. The PRD did not say, and UI_PLAN §5 covered only the 403 case. Two 404s that differ in wording or shape still let an outsider walk the id space — hence the equality assertion in `tests/rbac/` rather than a status-code check — Vishnu
- 2026-09-21 — An **admin-only mutation answers 403 uniformly for every brand id**, because the role gate runs before any lookup. That is not a leak — the reply does not depend on the brand — so the test asserts uniformity rather than forcing a 404 through a role gate. Written down because the first version of the test asserted 404 and was wrong — Claude
- 2026-09-21 — **FR-4 amended: invites do not need SMTP.** FR-10 (the SMTP profile) is P1 and lands in Stage 4, so invites literally could not be emailed in Stage 1. An invite returns its link once, in the creation response, and the UI shows it with a copy button. When SMTP arrives, emailing becomes an addition, not a rewrite — Vishnu
- 2026-09-21 — **Invite and reset tokens are show-once, hash-only.** Only the SHA-256 is stored, so a database leak cannot be replayed into an account. A lost link is recovered by "New link", which rotates the token and kills the previous one — chosen over storing the token encrypted for re-display — Vishnu
- 2026-09-21 — **One `invites` table serves invites and password resets**, separated by `purpose`, because the rules are identical (hash only, single use, expiry, revocable) and duplicating that logic is how one copy drifts. Expiry differs: 7 days for an invite, 24 hours for a reset. The purpose is part of the token lookup, so the two flows cannot be crossed — Claude
- 2026-09-21 — **Sessions are opaque ids in Redis**, not a stateless token: deactivating a user, resetting their password or changing their own must revoke access on the next request, which a self-contained token cannot do. Redis already runs with `appendonly yes` and a volume, so a restart does not sign everyone out — Vishnu
- 2026-09-21 — **Login rate limits: 10 per 15 min per IP, 5 per 15 min per email**, sliding window in Redis, both consumed before any credential check so a flood cannot probe passwords. The email is hashed into the key — the counter does not need to know who it is counting. An unknown email and a wrong password return byte-identical 401s, and one argon2 verify always runs, so neither body nor timing reveals whether an account exists — Vishnu
- 2026-09-21 — **CSRF is double-submit** and the token **rotates on sign-in** (session fixation). The frontend therefore reads the cookie per request rather than caching it — a cached token 403s every mutation after login, which is how the rotation was found — Claude
- 2026-09-21 — **The seeded super admin starts with `must_change_password`.** Every route except the change-password screen refuses until it is done, so the password in `infra/.env` stops being a working credential the first time it is used. The seeder refuses to create an account when the password is blank rather than making one with no way in — Vishnu
- 2026-09-21 — **Lockout guards:** nobody can demote, deactivate, un-grant or password-reset themselves, and the last *active* super admin cannot be demoted or deactivated (an inactive one does not count as cover). These are the clicks with no undo from inside the UI — Vishnu
- 2026-09-21 — **Auth events are audited**: login success and failure, rate-limit trips, logout, password change, reset issued and used, and sessions revoked on deactivate. Email and IP are recorded; the audit service strips any key that looks like a credential before writing, and a test asserts no password reaches the log — Vishnu
- 2026-09-21 — **Archived brands are invisible to members**, grant or no grant, and `archived=all` is forced back to "active" for them rather than trusting the query parameter. Admins see them behind an "Archived" filter — Vishnu
- 2026-09-21 — `exactOptionalPropertyTypes` is **off** in `tsconfig.json`; everything else stays strict. It is not part of `strict`, and TanStack Table's `ColumnDef` is invariant in its value type under it, so every column definition in the app would need a cast — and CLAUDE.md mandates TanStack Table for all tables — Claude
- 2026-09-21 — shadcn primitives are **hand-written against the THEME.md tokens** rather than pulled with `npx shadcn add`. ## 2026-09-22 — the runs that sat at "queued"

- 2026-09-22 — **Connection pools are cached per event loop, not per process.** "Test login" left every second run stuck at `queued` for ever. The worker calls `asyncio.run()` once per Dramatiq message across two threads, and both the SQLAlchemy engine and the redis-py pool were module globals — so the second task on a thread checked out a connection belonging to a loop that had already closed: `RuntimeError: got Future attached to a different loop`. It struck inside `session.get(Run, run_id)`, *before* the run's own error handling, so nothing marked the run failed and the UI waited on it indefinitely. The run table shows the signature plainly: succeeded, queued, succeeded, queued. `get_engine()`, `get_session_factory()` and `get_pool()` now key their cache on the running loop, and `dispose_engine()`/`close_redis()` close only the running loop's own — a task cleaning up must not pull the pool out from under another thread. The API and scheduler each run one long-lived loop, so their pooling is unchanged — Claude

## 2026-10-01 — Cancelling a run (FR-35), and a finished run stays finished

- 2026-10-01 — **A Cancel is one Postgres transaction.** `POST /runs/{id}/cancel` locks the run row (`FOR UPDATE`), then sets the run to `cancelled`, every unfinished task to `cancelled`, adds the timeline event and the audit row, and commits it all at once. If any part fails, none of it lands. Announcing it over SSE and freeing the login lock happen after the commit, and are best-effort: the cancel is already true, so a Redis blip doesn't turn it into a 500 — Claude
- 2026-10-01 — **What a Cancel keeps:** tasks that already finished keep their outcome, and their files stay. The report downloading at that moment is abandoned, and queued reports aren't pulled. A Cancel stops what's left; it doesn't undo what's done. A run that has already finished answers 409, so a double click doesn't read as a second cancel — Claude
- 2026-10-01 — **Who may cancel is who may start.** Admin and above; a Manager on the brand; an Executive only with `can_trigger_runs`. A test login has no brand, so only its starter may cancel it. Seeing a run isn't enough. `RunDetail.can_cancel` says whether the viewer may, so the button appears only where it would work — Claude
- 2026-10-01 — **`set_status` is a compare-and-set: it changes a run only while `finished_at IS NULL`.** The worker, the stale-run sweep and a Cancel race to end a run, and the first to finish it now wins. Before this, a worker the sweep had wrongly marked `WORKER_LOST` kept going and set its run back to `running`, and a cancelled run came back the same way (run #161). The sweep now claims the run before writing its `WORKER_LOST` event, so a run its worker has just finished isn't also reported lost — Claude
- 2026-10-01 — **The worker holds the run row while it commits a task's outcome** (`_hold_open`, before every task commit). The files, their `is_latest` flips and the task's success commit together, or, if the run was cancelled in the meantime, none of them do. The run row is always locked before the task rows (`no_autoflush`), the same order as the Cancel, so the two can't deadlock. If the run has ended, the worker raises `RunClosed`, a `BaseException` so that no `except Exception` retry loop treats "this run is over" as a portal hiccup — Claude
- 2026-10-01 — **The worker learns of a Cancel by reading the database, not from a message.** `watch_run` polls the row every 5 s, and when the run has ended it stops the run's coroutine. The browser then closes and the login lock is released by their own context managers. A message published after the commit would be lost if the API died between the two; the row can't be lost — Claude
- 2026-10-01 — **The heartbeat comes from the same watcher, every 5 s.** It used to be written once per report with a 300 s TTL, so any report slower than five minutes (every Zepto Ads report takes 14–16) looked like a dead worker and was swept as `WORKER_LOST` mid-download — Claude
- 2026-10-01 — **A re-delivered job for a finished run does nothing** (`workers/tasks.py`). When a worker restarts, Dramatiq re-delivers the job it was killed during; without this check the run started over from its first report — Claude
- 2026-10-01 — **The login lock records which run holds it, and is released only by that run.** `lock:account:{id}` used to hold `"1"`, and every run deleted it unconditionally on the way out, so a run longer than the lock's one-hour TTL freed the next run's lock. Cancelling a run whose worker has already died also releases its lock, but only when its heartbeat has lapsed and the lock names that run: a live worker releases its own lock, after its browser has closed — Claude

## 2026-10-02 — Unified Ads DB phase 2: loader, cross-report checks and the admin screens

- 2026-10-02 — **A cross-report "must equal" check holds or pulls back data only within one pull.** One pull = the same run, or the same chunked series (`runs.options.series`); a 3 h `extracted_at` window applies only to files without a run. Bug A1 happens inside one run (that run's files carry the wrong day), while reports pulled on different days legitimately differ (Zepto: up to ₹5 of spend between reports pulled days apart, impressions exact). Across pulls the same comparison is the soft check `drift:<rule>`: it records the gap, never holds anything, and the newest pull wins per slice. Supersedes the doc 21 §3 sentence "a miss holds the load that arrived second and flags the other": with that rule, a ₹2 campaign re-pull blanked whole dates, and the result depended on arrival order — orchestrator, after adversarial verification
- 2026-10-02 — **A miss within a pull trusts neither side.** The file that arrived is quarantined, and that pull's current loads of the date are pulled back in one pass: the headline, every report with a must-equal rule against it, and its coverage partners (SP city, keyword). The date shows nothing until a later pull. A dispute holds the rest of that pull's files for the date, keyed on (brand, date, family, pull), and never holds a later pull. A held load acts on nothing, and another pull's loads are never pulled back, so a bad re-pull lets the previous consistent pull return. When the headline is absent, a report is compared with its siblings, with their tolerances added — Claude
- 2026-10-02 — **A range-tiling miss pulls back every day load of that report inside the range, whichever side arrived second** (doc 21 §3). Ranges missing some days are checked too: the sum of the days present must be ≤ the range plus tolerance (impressions, clicks and spend). A range minus a range nested inside it is tiled as well. Orders are never compared; Zepto restates them for more than 7 days. Known effect: a miss on a long stored range (1–29 Sep) blanks the month for that report; scheduled range pulls are weekly.
