Each column of each report, and what happens to it at each stage: Raw, Staging and Our database.

Three stages: Raw → Staging → Our database

Every downloaded file passes through all three. Raw and Staging keep every column exactly as Zepto sent it. Columns are only treated differently in Our database, as the table below shows.

The 7 checks before data reaches our database
  • Every expected column is present.
  • Every row of the file is loaded exactly once.
  • Totals of Spend, Impressions, Clicks and Revenue match the file.
  • Zepto's CPC, CPM, CTR and ROAS match our own calculation (at most 1% of rows may differ).
  • The brand in the file is the login's brand.
  • Dated rows fall inside the requested range.
  • No two rows share the same key.

The five treatments in Our database

Stored as number

Text in the file becomes a number in its own column. These can be added up across rows and days.

Kept as-is

Stored exactly as Zepto wrote it, in the reported field. Never added up: averages, unknown definitions, unique counts.

Label

Names and IDs: campaign, keyword, city, page, product. They go to lookup tables or become the row's key.

Checked, then recalculated

Zepto's ratios (CPC, CPM, CTR, ROAS) and halo orders. We check each one against our own calculation, so a broken file is caught. We don't store them; dashboards recalculate them from the totals.

Brand check

Must match the brand the login belongs to, or the whole file is rejected. We store our own brand id instead.

Added by us on every row

Zepto's file doesn't contain these, so we add them:
  • Date range (period_start, period_end): the range we asked Zepto for, because the file has no dates.
  • Brand (brand_id): the brand whose login downloaded the file.
  • Ad type and report (ad_product = 'sp', report_key, breakdown).
  • Where it came from (report_file_id, load_id, observed_at): a link back to the original file. A re-download replaces older rows (superseded_at) rather than deleting them.
